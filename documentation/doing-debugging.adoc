== Current Report

The Rust service exposes completed band timings in `GET /api/state` as `band_timings` and includes them in the run outcome. Each record describes one raster band. For a multi-band run, sum the records for a run total.

[cols="1,3",options="header"]
|===
| Field | Meaning
| `transfer_ms` | Time spent sending raster data, including any retries.
| `setup_ms` | Raster preparation and protocol setup outside transfer and completion wait.
| `wait_ms` | Time waiting for K6 completion status after setup.
| `elapsed_ms` | Total elapsed time for the band.
| `phase` | `reported_complete` means the device reported completion; `assumed_complete` means the service observed 90 seconds of silence.
| `percent` | Device-reported progress for this band; it is not the percentage for the full side or card.
|===

The timing values are milliseconds. Small differences between summed component times and elapsed time can result from measurement boundaries and millisecond rounding. Assumed completion is not device confirmation.

== Historical Measurements

The following measurements are from the retired Python service and are not Rust performance claims.

* A 1600x1600 raster used a 320,000-byte payload in 169 chunks. Transfer took 35.8 seconds, about 8.7 KB/s, with approximately 208-210 ms per chunk.
* In that run, the first observed completion status arrived about 4.9 seconds after data transfer. The first observed percentage was 37%; earlier progress was not captured.
* In a separate completion-detection run, the estimated duration was 336 seconds while the observed burn lasted 889 seconds. The old monitor stopped early; this observation informed later completion handling.

These are dated observations from specific runs. Use `band_timings` to see how a current Rust run divides time among setup, transfer and completion wait.
