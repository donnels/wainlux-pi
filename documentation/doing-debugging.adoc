== Current Report

The Rust service exposes completed band timings in `GET /api/state` as `band_timings` and includes them in the run outcome. Each record describes one raster band. For a multi-band run, sum the records for a run total.

[cols="1,3",options="header"]
|===
| Field | Meaning
| `transfer_ms` | Time spent sending raster data, including any retries.
| `setup_ms` | Raster preparation and protocol setup outside transfer and completion wait.
| `wait_ms` | Time waiting for K6 completion status after setup.
| `elapsed_ms` | Total elapsed time for the band.
| `phase` | `reported_complete` means the device reported completion; `assumed_complete` means the service observed 90 seconds of silence.
| `percent` | Device-reported progress for this band; it is not the percentage for the full side or card.
|===

The timing values are milliseconds. Small differences between summed component times and elapsed time can result from measurement boundaries and millisecond rounding. Assumed completion is not device confirmation.

Card review responses also report raster-generation and preview-encoding milliseconds. The browser and CLI report their own review round trips, which include transport and client-side work and are not additive server phases. The outcome's `elapsed_ms` covers the prepared operation sequence. The UI breaks its measured band totals into transfer, setup and laser feedback wait, with the remaining operation time shown separately. Audio upload/analysis response time is a different workflow and is labelled separately.

For interpretation, the UI can open a self-contained real-run sample at `GET /examples/audio-analysis`. It demonstrates decoded sync ID and candidate activity beside run-log markers. This one sample is not a process capability study: use repeated comparable runs, retain the defined measurement boundaries and analyze distributions before drawing Six Sigma conclusions. Acoustic activity remains a candidate, not confirmation of laser motion.

== Historical Measurements

The following measurements are from the retired Python service and are not Rust performance claims.

* A 1600x1600 raster used a 320,000-byte payload in 169 chunks. Transfer took 35.8 seconds, about 8.7 KB/s, with approximately 208-210 ms per chunk.
* In that run, the first observed completion status arrived about 4.9 seconds after data transfer. The first observed percentage was 37%; earlier progress was not captured.
* In a separate completion-detection run, the estimated duration was 336 seconds while the observed burn lasted 889 seconds. The old monitor stopped early; this observation informed later completion handling.

These are dated observations from specific runs. Use `band_timings` to see how a current Rust run divides time among setup, transfer and completion wait.

== Audio Sync and Candidate Motion

Use the containerized analyzer from the repository root:

.Analyze an audio recording and correlate it with the API log
[source,bash]
----
./scripts/analyze_laser_audio.sh /path/to/recording.m4a \
	--run-log /path/to/sanitized-run-log.json \
	--attempt-id ATTEMPT-ID --expected-id DDDDDD
----

The current upload report includes the recording for playback, its decoded ID when available, a full-length auto-scaled min/max amplitude waveform with time/amplitude zoom, seek and Jump to end, timestamp-aligned receive bytes/decoded frames when captured, run-log markers, and measured processing timings. The packet table lets operators inspect which received values preceded progress/completion events; untraced runs explicitly lack those packet events. It does not classify audible activity or infer laser state. The Analysis tab compares the latest ten run goals/settings and durations, with links to individual uploaded reports and optional side-by-side waveform views. The in-app `/examples/audio-analysis` page is an older exploratory report.

The M4A creation-time tag differed from the API marker wall clock by about 2 h 40 min even though the audio DTMF ID matched. Use the ID for association; do not treat file metadata as a physical timing reference. The analyzer uses FFmpeg 5.1.9 in its pinned container and Python standard-library Goertzel analysis for the sync ID; no audio packages are installed on the Deck.

The current detector still waits 90 seconds after the final received byte. The run log, measured timings and recording playback do not prove exact physical stop.
