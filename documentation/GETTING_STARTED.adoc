== For Users

=== Deploy to Pi

.Start the preloaded ARM image
[source,bash]
----
cd docker/docker-wainlux-rs
docker compose up -d
----

Access: `http://<pi-ip>:8081`. The ARM image must already be loaded on the Pi; this compose file does not build it.

=== Build and Test the Rust Service

Build on the Steam Deck or another development workstation, not on the Pi Zero W. Run the one canonical build command from the repository root:

.Test Rust, then build the Pi image
[source,bash]
----
./scripts/build_laser.sh
----

The script runs `cargo test --workspace --locked` in a pinned Rust container, then builds the service Dockerfile for `linux/arm/v6` as `localhost/laser-app:arm`. The release binary is compiled for the Pi Zero W's `arm1176jzf-s` CPU; the container platform selects the matching ARMv6 runtime image. The Cargo registry and compiled host test artifacts persist in named volumes `wainlux-pi-cargo-registry` and `wainlux-pi-cargo-target`. Repeated tests reuse the target volume; the ARM release build is a separate target and is rebuilt when source changes invalidate the container build cache. The Cargo lockfile, target platform, test image, cross-compiler image and runtime image are fixed inputs. The result uses the same local image name as the Pi Compose file.

The script prefers a running Docker engine, then Podman; `CONTAINER_ENGINE=docker` or `CONTAINER_ENGINE=podman` selects one explicitly. In a Flatpak, it prefers `flatpak-spawn --host` so piped data such as an image stream reaches SSH correctly, then falls back to `host-spawn`; outside Flatpak it invokes the engine normally. Install and start Docker or Podman on the host. No host Rust toolchain is needed. It does not push, transfer, load, or deploy the image to the Pi.

The image digests are intentional pins. When updating them, verify the replacement manifests still include the build platform and `linux/arm/v6`, then rerun the build command and documentation checks.

=== Analyze a Run Recording

Analyze a phone recording without installing audio software on the workstation:

.Match the recording to run logs and processing timings
[source,bash]
----
./scripts/analyze_laser_audio.sh /path/to/recording.m4a \
	--attempt-id ATTEMPT-ID --expected-id DDDDDD
----

The script builds/reuses the pinned `docker/docker-audio-analysis` container, mounts the input and optional API log read-only, prints a JSON report, and writes the HTML report beside the recording. The HTML embeds a browser-compatible mono MP3 preview up to 40 MiB; larger reports write an MP3 sidecar. The analyzer decodes the optional DTMF recording ID only to associate it with the attempt, then reports filtered run-log events and measured processing timings. It does not classify audible activity or infer motion or laser state. Docker or Podman must be available on the host; Flatpak host routing is handled by the shared script helper.

The UI's **Machine tests > Archived exploratory audio report** opens an earlier self-contained example built from an actual 2 mm frame recording. Its sound-activity annotations are historical and are not generated by current uploads. The source recording is embedded in that archive; the old `Verification/` working folder is not needed.

For a manual iPhone Voice Memos recording, use Share in Voice Memos and save the `.m4a` to Files, then transfer it to the analysis host. Analyze it with the matching attempt and a sanitized API log export:

.Analyze a manually imported iPhone recording
[source,bash]
----
./scripts/analyze_laser_audio.sh /path/to/voice-memo.m4a \
	--run-log /path/to/sanitized-run-log.json \
	--attempt-id ATTEMPT-ID --expected-id DDDDDD
----

=== Phone-Driven Audio Sweep and Upload

For ordinary Real card or machine runs, the planned-run screen also offers an optional Voice Memos recording confirmation. Start the recording and check it before starting; the Pi plays the attempt ID cue and logs the association. After a completed marked run, upload is offered only if the optional analyzer is available. This does not block the burn, and logs/timings remain the primary record. Keep the original in Voice Memos if upload is unavailable.

The analyzer-gated audio test offers two separate choices over the same 20 mm box plus nine 19 mm lines: minimum nonzero power (1/1000, nominally no-mark but not guaranteed) and full power (1000/1000, marking expected). Each is a distinct, human-started run; the full-power comparison is never triggered automatically. Use sacrificial stock and keep the beam path clear for both. In Real mode, the UI requires confirmation that Voice Memos is recording, then plays the attempt ID cue before the human confirms the run. After completion, choose the iPhone-exported `.m4a`. The Pi forwards it with only the matching sync marker/run outcome and retains no audio or HTML. The analyzer stores audio, filtered events, and the report under `docker/docker-audio-analysis/data/ATTEMPT-ID/`. It has no restart policy: stopping it releases resources and hides both audio profiles/report controls, while ordinary burns continue normally.

The measured 50.15-second sample was 836,997 bytes. A successful Wi-Fi card content run lasted 2,054 seconds; at the observed rate, with 36 seconds of recording margin, the estimated file is about 33.3 MiB. The matching Pi/analyzer upload cap is 64 MiB, roughly 1.9x headroom. Actual Voice Memos bitrate and duration may vary.

Run the analyzer on the Deck only when tuning or reviewing test evidence. Keep the shared bearer token out of source control and restrict the analyzer port at the host firewall to the Pi:

.Start the external analyzer on the workstation
[source,bash]
----
export AUDIO_ANALYZER_TOKEN='set-the-same-private-token-on-both-hosts'
export AUDIO_ANALYZER_BIND_ADDRESS=0.0.0.0
podman compose -f docker/docker-audio-analysis/compose.yaml up -d --build
----

In the Pi's `docker/docker-wainlux-rs/.env`, set `AUDIO_ANALYZER_URL` to `http://WORKSTATION-LAN-IP:8090/api/analyze` and set `AUDIO_ANALYZER_TOKEN` to the same secret. Keep `.env` private. Recreate the Pi service after setting these values. The analyzer's port is loopback-only by default; only bind it to the LAN after firewalling access to the Pi. When analysis is no longer needed, stop the optional container:

.Stop the analyzer without affecting the Pi laser service
[source,bash]
----
podman compose -f docker/docker-audio-analysis/compose.yaml down
----

Its bind-mounted data remains on the Deck and is available when the container is started again. With it down, the Pi hides the audio-only test and report features. Standard test and burn controls are unaffected.

If the Pi proxy or analyzer is unavailable, the separate CLI workflow above remains usable after transferring the `.m4a` and a sanitized matching run-log export to the analysis host.

To move the finished image from the Deck to the original Pi Zero W, first make sure no job is running and no in-memory review needs to be kept. Then explicitly deploy:

.Transfer, load, and restart the Pi container
[source,bash]
----
./scripts/deploy_laser.sh --target sean@piz-k6.local --confirm
----

Replace the example host with the SSH name or IP for the intended Pi, or set `LASER_SSH_TARGET` in the environment. The script refuses unless the remote model is Raspberry Pi Zero W Rev 1.1 (`armv6l`) and the service API reports idle, Simulator mode, no attempt, no outcome, and no loaded review. It streams the already-built ARM image from the Deck, verifies the loaded image ID matches, and recreates `laser-app` through the Pi's Compose file. SSH host-key verification remains enabled. The Pi only loads and runs the image; Rust compilation stays on the Deck. The script never starts a laser job.
