= ADR-029: Local Container Builds for Supply Chain Security

== Status

Accepted.

== Context

The project relies on containers for builds, documentation, analysis, and local services. Mutable remote tags and unlocked dependencies make those tools hard to audit and reproduce. A scanner gate must protect image updates without preventing ordinary work when a candidate fails.

== Decision

* Define project containers with local Dockerfiles under `docker/`. Keep each image's files and short README in its image directory.
* Pin external base images by immutable digest. Lock application dependencies with committed lockfiles or hashes.
* Build a uniquely tagged local candidate and scan that exact image before promotion. HIGH and CRITICAL findings block promotion by default.
* Promote only a passing candidate to the local tag used by scripts and Compose. Preserve the previous selected image and retain failed candidates for review.
* Keep image maintenance separate from task execution. Task scripts use selected local images and do not pull, rebuild, or scan implicitly.
* Permit a finding exception only when it names the image and finding, limits use, states a reason, and expires. Scanner operational failures cannot be overridden.
* Use the digest-pinned Trivy image as the scan trust root. Do not scan it with itself.
* Keep the image inventory and update procedure in `docker/IMAGES.adoc`; put scanner usage in `docker/docker-trivy/README.adoc` and image-specific scan evidence in each image README.

== Consequences

* Image inputs and scan evidence can be reviewed in the repository.
* A failed candidate does not replace the working image.
* Builds and database refreshes need network access.
* A retained image can gain newly known findings when Trivy's database changes. Explicit rescans are required to review them.
* Maintainers must update digests, locks, hashes, and exceptions deliberately.
