= ADR-032: Run Capture and Artifact Retention

== Status

Accepted; implemented.

== Context

Run logs and audio are useful for debugging protocol behavior and comparing runs. They can also consume storage and expose card content. In particular, transmitted raster bytes can encode a QR code or other image and must be treated as sensitive data.

The Pi uses a small persistent data volume whose contents are harder to inspect during maintenance. The analyzer runs on a larger operator host, but its data directory also needs a firm bound. The Pi must retain undelivered artifacts so an analyzer outage does not silently lose a run.

The latest 33-minute run lasted about 2,018 seconds. Its trace reached both current capture limits (1,024 received bytes and 2,048 events) and was truncated. The observed retained trace was about 356 KB as JSON. A complete estimate with 25% headroom is about 1.5 MB for this run. This is a measured planning baseline, not a maximum for future jobs.

== Decision

=== Capture Levels

Enable serial tracing by default. Disabling debug tracing turns off serial logging and hides trace controls. Provide two capture levels while debug is enabled:

* **Protocol trace (default):** stream every received byte, command boundaries, non-raster command bytes, timestamps, acknowledgements, status frames, and errors to a per-attempt artifact. Do not store `DATA` raster payloads.
* **Raster trace (explicit opt-in):** also store the bytes sent in `DATA` payloads. Require confirmation before the job starts. These bytes can reconstruct the burned image, including QR data.

The trace is append-only during a run. Finalize it with completion state, byte/event counts, and a completeness flag. A trace limit must produce an explicit incomplete result; it must never silently discard old events and call the trace complete. Use 4 MiB as the initial per-run cap, subject to measurement against more captured jobs.

=== Pi Rolling Store and Delivery Queue

Keep the latest ten completed job bundles on the Pi after successful analyzer delivery. A bundle contains the run summary, trace artifact, and any delivery state. Keep pending-delivery bundles even when they are older than the ten-job window. Delete a bundle only after the analyzer confirms durable receipt and the bundle is outside the rolling window.

Use an idempotent per-attempt upload and a persistent retry queue. The Pi remains the capture source of truth. Do not block laser execution on report generation or network delivery. If the local spool cannot reserve space for the configured trace limit before a run, reject starting another run with a clear storage error. Never run a job while knowingly unable to retain its required trace.

=== Analyzer Retention

Use a size-based policy. The analyzer data directory has a 4 GiB managed-artifact limit. Keep a rolling unpinned set within a 1 GiB budget. The pinned set has a separate 3 GiB ceiling. Count logs, traces, uploaded audio, reports, and temporary staged files against the relevant budget.

When new unpinned data arrives, evict the oldest unpinned attempt artifacts until the rolling set fits. Never evict pinned data automatically. A pin operation that would exceed the pinned ceiling must fail clearly. If pinned data and in-progress uploads leave no room for a new artifact, return an explicit capacity error; the Pi retains and retries the pending bundle.

Keep pin state durable across restarts.

Pinning prompts for confirmation. If the attempt used raster capture, warn that the retained bytes can reveal the card image or QR data. Show which artifacts are present before confirming. Unpinning makes an artifact eligible for oldest-first eviction; it does not delete it immediately.

=== Analysis Availability

Generate a run timeline for every delivered job. Audio is optional. An audio upload adds a recording to that attempt's existing analysis. Keep analysis generation separate from raw artifact capture and delivery state.

== Options Considered

=== Age-Based Retention

Delete unpinned artifacts after a fixed period, such as 90 days.

* Simple to explain.
* Does not bound storage when jobs arrive quickly or recordings are large.
* A quiet system can retain stale data indefinitely relative to available disk.

=== Count-Based Retention

Keep a fixed number of unpinned attempts.

* Easy to inspect and predict by job count.
* Storage per job varies. At the existing 64 MiB audio upload limit, 50 attempts could consume more than 3 GiB before reports and traces.
* Does not protect the volume from a few unusually large artifacts.

=== Size-Based Retention (Chosen)

Bound the analyzer directory by bytes and evict the oldest unpinned attempts first.

* Gives a hard upper bound on managed storage.
* Handles mixed audio and log-only jobs better than a count limit.
* Requires accurate accounting, upload reservations, and visible behavior when pinned data blocks new retention.

== Consequences

=== Positive

* The Pi keeps a small recent window and does not discard undelivered jobs.
* The analyzer can retain more than the Pi's ten-job window while keeping a bounded footprint.
* Pinned comparison runs survive normal rotation.
* Raster payload capture is explicit and separated from the default protocol trace.

=== Negative

* A 4 GiB cap is a policy choice and may need adjustment after measuring real audio and trace sizes.
* Pinned artifacts consume capacity until explicitly unpinned or deleted.
* The Pi may refuse a new run when its pending spool cannot guarantee trace storage.
* A configured per-run trace limit cannot guarantee complete capture for arbitrarily long or high-volume jobs; reaching it must be reported as incomplete.
