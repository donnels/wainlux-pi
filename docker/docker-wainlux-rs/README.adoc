= Laser Service API

Standalone Pi Zero service. Clients submit content; the operator reviews exact 1-bit rasters and starts each burn separately. `GET /api` serves this contract. The browser and external clients use the same endpoints. OpenAPI 3.1 is at `GET /openapi.yaml`; Swagger UI is at `GET /docs` and enables Try It Out for GET only. License notices are in `app/assets/swagger-ui/`.

== Timing

Progress percentages are band-local, not full-side/card progress. `GET /api/state` exposes terminal bands in `band_timings` and the run outcome. Each band records `transfer_ms`, `setup_ms`, `wait_ms` and `elapsed_ms`. Sum them for run totals. Values are milliseconds.

After 90 seconds without a received byte, completion is assumed, not device-confirmed. The UI labels this separately; the next band event records whether the previous band was assumed complete.

Each review response includes `timing.raster_generation_ms` for composing stage rasters and `timing.preview_encoding_ms` for PNG/SVG preview encoding. The browser reports its own review-request round trip; the CLI prints its client round trip separately. These boundaries overlap and must not be added as if they were disjoint server stages. Each run outcome includes `elapsed_ms`; its band measurements split K6 transfer, protocol setup and completion feedback wait. The Inspection panel shows those components and the residual outside bands. For audio upload, the response includes Pi receive/prepare/total, analyzer persistence/process/report-read/total and nested analyzer sub-phases. The browser separately reports its upload/analysis response and report-download time. Analyzer sub-phases are inside the analyzer process duration; do not sum overlapping measurements.

`GET /examples/audio-analysis` serves one self-contained report generated from a real recorded 2 mm frame test. It is an interpretation example, not a benchmark, statistical baseline or proof that audible activity is machine motion. Its embedded sample is loaded only when the user expands the example in the UI.

Power-sweep and sync-marked attempts also return a bounded `receive_trace` in `GET /api/state`, the run outcome and the audit log. It includes per-job indices, monotonic event timestamps, raw received bytes, decoded frame names/bytes, progress, quiet intervals, duration, captured-byte count and truncation status. Command writes made through the request/reply driver path have write-return timestamps and protocol bytes, except DATA payloads are always omitted. Bulk DATA transfer start/end/error events form spans; band metadata records row range, geometry, power and depth. This is not a complete wire capture: out-of-band STOP and direct-write paths are not included. Capture is capped at 1,024 RX bytes and 2,048 events per attempt. It contains no outgoing DATA/raster bytes or user content. The UI displays the trace after the run. Instrumentation does not change the 100% completion rule or the 90-second silence assumption.

Audio reports use a shared clock for the signed waveform and separate Laser RX, Host TX, Jobs / bands and Run / sync lanes. The full recording fits at 1x; up to 128x redraws a continuous min/max envelope from 2 ms signed 16-bit bins of the decoded mono 8 kHz signal. At high zoom, minor ruler ticks are 200 ms apart; fractional labels appear where pixel spacing permits. These display intervals are not a claim of sync accuracy. A draggable overview window, its resize edges, horizontal scrolling and keyboard panning replace the timeline-position slider. Amplitude accepts 0.25x through 32x with peak-relative or full-scale reference. Selecting a packet or table row retains its decoded/raw details without seeking; a separate action seeks playback. The red cursor spans every lane and reports its time and difference from the selected event. Template/review/stage and band metadata identify jobs without retaining private card content. Truncation and unavailable historical traces are explicit; missing packets or job boundaries are not reconstructed from sound. A software finish marker remains duration-aligned to the nominal request, not an observation of stopped motion.

When a trace budget fills, older packet events are evicted while job/transfer boundaries and recent progress remain available within the same limits. The trace is marked truncated; it is not a complete packet history. This keeps late progress and software-completion events available for audio comparison on long recordings.

== Run Analysis With Optional Audio

When an analysis URL and token are configured, ordinary runs also enable bounded event capture without requiring a recording or sync cue. After a Real attempt finishes, a background request checks the existing analysis container and submits only the completed, redacted `ran` event. Device completion, subsequent operator actions and ordinary burns never wait for analysis; an unavailable container produces no report and does not change the outcome.

The existing audio analyzer accepts `application/json` at its unchanged `/api/analyze` endpoint with `attempt_id` and `run_log`. It persists a timing-only report without FFmpeg or an audio file. The report labels time since trace start (or run start when no trace exists), shows recorded RX/TX/job events and band timings, and explicitly marks audio absent. It never invents historical packets, sync sounds or physical completion. A later recording upload can replace the timing-only report with an audio-aligned report; a log-only request does not replace an existing audio-backed report.

The Analysis tab links either kind of report. `POST /api/audio-analyses/{attempt_id}/report` requests an existing completed Real run's report when the container is available; its Analyze action permits backfilling older runs. Old runs without a saved trace can show only recorded summary/band timings. Success appends the compatible `audio_analysis` audit event with `has_audio=false`; recording uploads use `has_audio=true`. The newest event determines the current report. The Pi retains neither report HTML nor media. Container, route and configuration names remain unchanged.

== Audio Recording Sync

For Real-mode UI runs, the checked-by-default audio cue plays a short three-tone preamble followed by six standard DTMF digits. The six digits are the last six decimal digits of the planned attempt's timestamp ID and are shown in the planned-run panel. Leave the computer's speakers audible to the phone recorder; the cue takes about 2 seconds, followed by a logged 700 ms lead before `/api/run` is requested. The `sync_marker` audit event stores the attempt ID, six-digit recording ID, cue duration, lead and request timestamp. Use the digits in the audio filename or notes to match the recording to the run log. This is a timing marker, not confirmation of laser motion or completion.

A template can set `audio_recording_enabled = true` to show the optional Voice Memos confirmation for Real card stages. The card action now plans first and waits on the planned-run screen; checking recording causes the cue/marker, then the operator explicitly starts the run. After an optional upload succeeds, `/api/log` receives an `audio_analysis` event with the attempt ID, phase timings and same-origin report URL only. The Pi does not retain audio or report HTML; analyzer availability does not gate ordinary burns.

The operator UI's Analysis tab shows the latest ten completed runs as a timing breakdown graph and links an uploaded report when available. Audio analysis allows up to 900 seconds of processing; the Pi waits 930 seconds for the analyzer. If analysis times out, the upload returns an error, but the analyzer retains the source recording and matching run log under its attempt directory. Re-uploading from the same attempt QR retries analysis.

== Submit and Review

Two submission forms are available. Neither opens the serial connection or starts the laser.

* Producer: `POST /api/jobs/review` with a `job` object: `template`, `piece`, `backing`, `placement`, `guide`, `items`, optional `values`.
* Template form: `POST /api/jobs/form` with `template`, `review_id` (`null` for a new idle review), `piece`, `backing`, `placement`, `guide`, and changed `fields` keyed by template field ID. Field edit policy is enforced.

A template may set `audio_recording_enabled = true` to show the optional Voice Memos confirmation for Real card stages. This checkbox is not a run prerequisite when left unchecked and never requires the analyzer to be available. Checking it makes the UI play and log the attempt-ID cue; after the completed run, upload is offered only if the optional analyzer is reachable. Dedicated audio profiles retain their stricter recording requirements.

Each item names a declared element `id`, `side` (`front` or `back`) and `content`.
Content kinds are `qr` (`text` payload), `text` (`text`, `font_size_mm`, optional `font`), `wifi` (network fields) or `image` (`asset_id`).
Positions and dimensions omitted by a producer come from the template. An image asset ID refers to prepared pixels; it is not an arbitrary URL or Pi path.

.Example vCard job with a prepared logo asset
[source,json]
----
{
  "job": {
    "template": "vcard",
    "piece": "bamboo-ntag215-light",
    "backing": "backing-first",
    "placement": "left",
    "guide": false,
    "items": [
      {"id":"contact-qr","side":"front","content":{"kind":"qr","text":"BEGIN:VCARD\nVERSION:3.0\nFN:Jane Example\nURL:https://example.com/cv\nEND:VCARD"}},
      {"id":"logo-back","side":"back","content":{"kind":"image","asset_id":"tiger"}}
    ]
  }
}
----

The response contains `review_id`, `template`, policy-projected `fields`, geometry-only `job`, `layout`, `display`, ordered `stages` and `accepted_stages`.
Each stage has `name`, `side`, `goal`, resolved `values`, and `burns` with PNG/SVG pixels, pixel dimensions and physical position/size.
Different sides are separate rasters, never composited together.
`guide=true` adds an optional guide stage before the front; existing markings can be reused with `guide=false`.

`GET /api/jobs/review` retrieves the current review. The UI discovers it from `GET /api/state` and loads it without a browser-file injection.
`POST /api/jobs/form` edits and regenerates a review using its current ID. Stale IDs, undeclared fields and forbidden edits are rejected.
`DELETE /api/jobs/review` explicitly discards an idle review; an active attempt blocks replacement/discard.

== Types

* `wifi-login`: network QR plus independently optional readable labels. Password is QR-only.
* `vcard`: producer-supplied vCard text or CV URL, optional readable contact label, optional logo back. The producer owns vCard serialization/escaping and contact data; the laser does not query neocv's graph.
* `github-recovery`: recovery payload QR on the front and login URL QR on the back. Small required-by-default captions identify “GitHub MFA recovery codes” and “GitHub login to use these codes”. Recovery codes are transport data, not printable page text. A second small, optional caption can print the login URL.
  An optional front checklist adds 16 blank boxes (2 columns x 8 rows) beside the recovery QR for manually marking used codes. It defaults off and does not contain or encode code values. A producer opts in by submitting a `use-checklist` item with `kind: checkboxes`, `count: 16`, `columns: 2`, `box_mm: 3.5`, `gap_mm: 0.8`, and `line_mm: 0.35` at the declared `check-x` / `check-y` position.

The repository's `cli/` card client only submits these same review requests. Its `inputs/wifi.json`, `inputs/github.json`, `inputs/vcard.json`, and `inputs/synthetic-codes.txt` are fictional demonstration inputs, not live credentials. `wainlux-client submit --text-file recovery-qr=FILE` loads codes from a UTF-8 file. The CLI has no PDF, QR, image or font generation; the Pi renders all card content.
The operator can also paste codes or load a codes-only UTF-8 `.txt` file into the masked recovery field. The browser reads the file locally; clicking Preview submits the payload through the existing review API. Do not use a file that combines codes with unrelated instructions or a password.
Fields declare optional `file_input` capability through `/api/templates`; only editable multiline fields may enable it. The browser uses that metadata for recovery-code and vCard file inputs, without template-specific form logic. File loading does not start a review or a burn; Review output submits it explicitly.
The client submits both `recovery-qr` (front) and `login-qr` (back) items. Small front/back purpose captions are on by default and carry no secret data; `include-url-text` is off by default and can add the URL as an additional caption.
Real recovery formats and line lengths must be previewed; overflow is rejected, not silently shrunk.
Private payloads remain in RAM, not template files or operational logs.

== Execute One Stage

. Review both sides before starting. Confirm placement.
. `POST /api/plan` with `review_id`, `stage` (zero-based) and `placement_confirmed` (`true` required for a back stage).
. Only `POST /api/run` starts the planned stage. Send `attempt_id` equal to the returned plan ID; a mismatch is refused without replacing the plan. The browser sends it on every start. Older clients may omit it; it is not authentication. A run never advances automatically to another user stage.
. Poll `GET /api/state`. `POST /api/stop` cancels queued driver work and requests stop; the operator confirms physical rest.
. Record `POST /api/verdict` with `status` (`ok`, `deviation`, or `skipped` for an unperformed plan) and an observation.
. A later stage requires accepted prior stages. Inspect the front, confirm motion stopped, flip the card and seat it against the same guide before planning the back.

.Plan the reviewed front stage
[source,json]
----
{"review_id":"returned-review-id","stage":1,"placement_confirmed":true}
----

An edited review clears stage acceptance. Re-running an earlier stage invalidates later acceptance. Simulator/Real mode changes clear acceptance too.
The K6's temporary completion policy assumes completion after 90 seconds without a response; it does not prove a physical OK.

== Trust and Lifetime

This is a trusted-LAN service, not a public authenticated API. Producer/operator role separation and session leases remain open.
Non-revealable fields are omitted from operator source projections, but visible raster/QR pixels can disclose their contents.
Reviews and acceptance are RAM-only; restart loses them. Do not write payloads into URLs, logs or template defaults.

== Clear Pi and Account State

The operator UI's **Options > Clear session** control calls `DELETE /api/state`. It clears the in-memory review, planned attempt, progress, and pending outcome, drops idle device handles, and refuses while a run is active. The redacted `runs.jsonl` audit log is retained; a clear event is appended. Clearing is not a laser command and does not prove or change physical machine state.

Authentication is not implemented; this remains a trusted-LAN service, so session clearing is not logout. A future sign-in/access boundary must be implemented independently and is not enforced today.

== Tests

Power and audio sweep previews composite the same positioned job rasters used for execution; line length and pixel rounding are not drawn by a separate schematic. Per-job powers and bed placement remain in the goal. Preview pixels do not simulate burn darkness or prove physical placement. Basic test dimensions are checked against reach before allocation, and QR-test goals omit payload text so audit logs do not retain it.

`cargo test --workspace` includes real-HTTP simulator tests for both new types, asset retrieval, front/back separation, stale review handling and manual flip gating.
`app/tests/ui.cjs` exercises the generic template editor and side controls using synthetic data. Safari/Firefox rendering still needs separate checks.
